# Assigned-clinician messaging and linked feedback

Third release of docs/features/expansion.md. The owner explicitly approved one private text conversation between patient and their currently assigned clinician, unread counts and manual refresh, with photo/routine feedback in the same conversation linked to its source. No file attachments.

## User flow

Add Messages as fourth native iOS tab and a portal navigation destination. A patient opens their current assigned conversation; an unassigned patient sees an accurate unavailable state. Clinician inbox lists current assigned patients with recent message and unread count, supports selecting an assigned patient with no existing messages, and opens one conversation. Patient workspace has a Messages link carrying patient context.

Newest messages appear first in retrieval but are rendered in chronological order within the loaded page; Older loads stable cursor pages without losing drafts. Explicit refresh retrieves new items; no claim of instant push delivery. A visible “Sent” state means accepted by server. Keep composer text/stable UUID through transient/lost-response failure; explicit retry cannot duplicate a message. No automatic retry to a newly assigned clinician. Bound content to trimmed 1–4000 characters, plain text only; render as text, never HTML.

Unread state changes only for received messages actually displayed, via an explicit authenticated acknowledgement of bounded exact message IDs. Fetching a page must not mark unloaded history read. Marking is idempotent, recipient-only and current-assignment checked. No typing indicator, delivery/read promises or response-time guarantee.

## Linked feedback

A clinician can start feedback from a shared photo or routine revision. The message contains a typed optional reference to that exact authorized record, never an arbitrary URL or user-supplied owner. Server verifies referenced record belongs to the conversation's patient and current clinician has access. Display a contextual link/date/name without embedding a signed photo URL into message storage. Opening reauthorizes at that moment; unavailable references show a truthful state. Patient replies use the same conversation. Existing historical records and review status are separate from message read state.

## Persistence and safety

Review the legacy messages API before reuse: it currently has unbounded lists, incomplete pagination, and a patient GET that marks all received messages read. Replace these behaviors for the active feature; do not expose legacy attachment URL fields or manufacture messages. Choose additive schema supporting typed UUID sender/recipient pair, server sent time, stable client ID/idempotency conflict, exact read acknowledgements and optional authorized record reference. Existing message records remain preserved; migration compatibility must be explicitly documented rather than silently dropping history.

Every read/write requires server-verified role/session and current assignment. Clinician A loses access after reassignment; old messages are not silently transferred to clinician B. Writes serialize against assignment changes via the patient-profile lock. Client account generation scopes requests, drafts and histories, rejecting late responses after sign-out. New tables have RLS and no direct public/anon/authenticated grants. No hard delete, retention policy, external notification provider, attachments or clinical response promise added.

## Acceptance

Focused tests: unrelated-role/assignment access denial; no cross-conversation reference; bounded stable pagination including equal timestamps; current recipient-only exact read acknowledgement; lost-response retry dedupe/body-conflict; revoked session/reassignment; account-switch stale response and preserved same-account retry draft. Real local synthetic patient-to-clinician and reply flow in both clients; unread count matches actual displayed messages. Care Journal light/dark/large-text and native tab behavior on changed surfaces. One integration/review wave; no camera test. Document hosted migration/API/client compatibility and remaining notification/response-policy limits.

## API

Mount `/api/assigned-messages` behind the existing server-verified `authenticateToken`; require the appropriate role at each endpoint. All JSON inputs are strict objects. UUIDs normalize to lowercase. Use the existing role spelling `patient | dermatologist` in DTOs, because clinician IDs are dermatologist profile IDs, not necessarily auth user IDs.

- `GET /current` (patient): `{conversation: Conversation | null}`. Null means there is no currently assigned clinician. Never choose a replacement destination in response to a pending send.
- `GET /inbox?limit=20&cursor=...` (dermatologist): `{conversations: Conversation[], nextCursor: string|null}`. Include every currently assigned patient, even with no messages. Smallest stable ordering is patient UUID ascending; last-message metadata is displayed but does not reorder pagination. Limit 1–50, reject malformed query values.
- `GET /patients/:patientId/clinicians/:clinicianId?limit=30&before=...` (either member): `{conversation: Conversation, messages: Message[], nextCursor: string|null}`. Messages newest first. Default 30, maximum 50. Refresh omits `before`; client merges by ID, and Older uses the oldest loaded page's cursor. Fetch has no read side effect.
- `PUT /patients/:patientId/clinicians/:clinicianId/messages/:messageId`: body `{content: string, reference: ReferenceInput|null}`. Message ID is a client-generated UUID created once with the draft. Content is trimmed, 1–4000 characters. Sender is derived exclusively from verified identity; recipient is derived from exact route pair. Patient sends require reference null; linked feedback creation is clinician-only. Response 201 on creation, 200 on exact replay: `{message: Message}`. A replay must match canonical trimmed content, sender, exact pair and reference, otherwise 409 `MESSAGE_ID_CONFLICT`. Do not disclose the conflicting existing message. First authorize current pair, then inspect replay, so old-assignment retries fail rather than return historical content.
- `POST /patients/:patientId/clinicians/:clinicianId/read`: body `{messageIds: string[]}` with 1–50 unique UUIDs. Require every ID exists in this exact conversation and was received by this identity. If any fail, reject the entire request with 404 `NOT_FOUND`; no partial acknowledgement. Update only these IDs where unread; response `{acknowledgedIds: string[], unreadCount: number}` includes already-read accepted IDs. No sender acknowledgement, ranges, implicit timestamps or “all read”.
- `GET /patients/:patientId/clinicians/:clinicianId/messages/:messageId/reference`: reauthorize exact current pair and message, then referenced record ownership. Return `{reference: ReferenceView, routine?: RoutineRevision, photo?: {id,captureDate,createdAt}}` with detail records at the top level and available false if the referenced record is unavailable. Available routine references additionally return the exact immutable revision (`id,userId,timeOfDay,version,name,isActive,steps,createdAt`); available photos return metadata `id,captureDate,createdAt` and clients use the existing freshly authorized original/thumbnail endpoint for pixels. No URL supplied by a client or persisted on a message.

`Conversation = {patientId: UUID, clinicianId: UUID, patientName: string|null, clinicianName: string, lastMessage: Message|null, unreadCount: number}`. Unread is relative to the requesting recipient, scoped to this exact pair. Pair is the conversation identity; no lazy conversation row or transfer operation is needed.

`Message = {id: UUID, patientId: UUID, clinicianId: UUID, senderId: UUID, senderType: 'patient'|'dermatologist', recipientId: UUID, recipientType: 'patient'|'dermatologist', content: string, sentAt: ISO8601, unreadForMe: boolean, reference: ReferenceView|null, origin: 'native'|'legacy'}`. Do not expose recipient read timestamps, attachment fields, database objects or storage paths. Accepted message response supports the UI label “Sent”; it is not a delivery promise.

`ReferenceInput = {type:'photo', id:UUID} | {type:'routineRevision', id:UUID}`.

`ReferenceView = ReferenceInput & {available:boolean, label:string|null, occurredAt:ISO8601|null}`. Derive labels/dates from authorized current records (photo capture date or exact revision name/date). If unavailable, retain type/id with null label/date and render “Photo unavailable” or “Routine revision unavailable”. Never replace a deleted/revoked exact record with the latest revision. Record review status is independent.

All unavailable/nonmember pairs return 404 `CONVERSATION_UNAVAILABLE`, malformed inputs/cursors 400, missing/revoked sessions retain existing 401, wrong-role endpoints 403. Unexpected failures use a generic message without clinical content.

## Persistence and paging

Add `assigned_messages` without altering or deleting `messages`. Columns: UUID primary key `id` (client UUID for native messages, original legacy UUID for imported rows); UUID patientId and clinicianId with Restrict foreign keys; checked senderType enum text; UUID senderId/recipientId plus checked recipientType derived consistently from the pair; text content; timestamp(3) sentAt with database default; nullable readAt; boolean legacyRead default false; checked origin; nullable referenceType/referenceId constrained both-null or one allowed type. For native content enforce trimmed length 1–4000. Legacy content is preserved byte-for-byte under origin legacy rather than silently truncated to satisfy a new bound. IDs of native entries and imported entries share a global uniqueness namespace; a collision is a 409, never an overwrite.

Use application authorization for typed reference ownership because a polymorphic reference FK cannot enforce both tables and a restrictive photo FK would unintentionally prevent existing photo deletion. Retain the ID when the record disappears. Reference ownership is checked under the patient lock on creation and each open; messages do not grant record access. Existing photo APIs treat the patient's uploaded records as accessible to the current assigned clinician; there is no independent per-photo sharing flag to invent. Routine revision may have been authored by a former clinician but can be linked if the current clinician is authorized for that patient's exact revision.

Index `(patientId,clinicianId,sentAt DESC,id DESC)` plus unread recipient/pair index. Determine unread as received by self AND readAt null AND NOT legacyRead. Native rows never set legacyRead. Keeping legacyRead preserves a historical boolean without fabricating a timestamp.

Message cursor is opaque base64url JSON `{v:1,patientId,clinicianId,sentAt,id}` with strict bounded decoding. Validate route-pair binding, timestamp precision and UUID. Query `(sentAt < cursor.sentAt) OR (sentAt = cursor.sentAt AND id < cursor.id)`, order sentAt DESC,id DESC, take limit+1. Cursor is a position, not authorization: every request freshly authorizes. It need not reference a still-existing row and cannot reveal another pair. UUID tie-break and millisecond DB precision avoid equal-date skipping. Server-generated time and immutable ordering fields ensure newly sent records do not shift older pages. New sends cannot specify timestamps. Inbox cursor is `{v:1,clinicianId,patientId}` and orders patientId ASC, with assignment freshly filtered on every page.

Use transaction patient `FOR UPDATE` then reload assignment for send and acknowledgement, matching routineCare. For reads use patient `FOR SHARE`, then authorize and read DTO rows while holding the lock. Inbox should select and lock its bounded candidate profiles in stable ID order and recheck assignment before fetching message summaries, to avoid a list/data TOCTOU. Ordinary assignment UPDATEs conflict with these row locks. Never query all clinician legacy history and only later filter patients (as the legacy inbox does). Concurrent identical sends serialize on the patient; handle global UUID unique races by retrying the transaction and performing the same conflict check, as routineCare does.

Enable RLS on new table; revoke all direct PUBLIC/anon/authenticated privileges and explicitly grant only the backend DB role required privileges. Do not expose direct client policies. Keep authentication's existing auth.getUser + auth.sessions verification and dermatologist-profile mapping; do not take sender roles/IDs from decoded token metadata or request bodies.

## Client invariants

Scope draft, UUID, reference, exact pair and pending request by authenticated account generation. Late responses cannot update a changed account's cache. Keep draft/UUID for explicit same-account retry after transient or lost-response failure; changing content/reference after failure requires a new UUID. Refresh/current lookup cannot retarget a pending send. Reassignment invalidates old composer/history and requires opening the new pair explicitly. Clear generation caches on sign-out without leaking persisted plaintext drafts across accounts. Acknowledge only received IDs after their messages are actually displayed, not every fetched row; virtualized/offscreen older pages remain unread until shown. Merge refresh/older results by ID and render chronological within loaded history.

## Release compatibility decision

Hosted legacy messages count was zero at September 13 preflight. Keep the legacy messages table untouched; retire its routes with authenticated 410 responses when the new API deploys. Do not build an import for nonexistent hosted history. Recheck count after retirement before client promotion; any unexpected legacy rows stay preserved and require an explicit import before claiming complete history. Local legacy security fixtures remain separate. Existing shipping iOS messaging is a placeholder and portal redirects to patients, so no active client messaging workflow is removed. New table origin may remain native-only; do not add unused legacy-read/import fields.
